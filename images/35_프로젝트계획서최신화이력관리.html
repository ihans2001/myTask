프로젝트계획서 최신화 이력 관리

프로젝트계획서는 초기 v1에서 멈춘 채 심사 때마다 지적받는 사문서가 되기 쉽다. 마일스톤마다 최신화 여부를 점검하고, 실제로 바뀔 때만 버전을 올리며, 이전 내용은 히스토리로 그대로 남긴다.
마일스톤별 버전 스탬프 신규항목 자동 편입 변경 이력 전량 보존
01왜 필요한가
초기 v1에서 멈춘 계획서
프로젝트 초반에 작성된 뒤 끝까지 그대로 유지되면 실제 진행 상황과 어긋난다
심사 때마다 지적받는 사문서
최신화되지 않은 계획서는 심사·감사에서 반복적으로 지적 대상이 된다
최초엔 없던 항목이 나중에 생김
프로젝트 초기엔 존재하지 않던 항목이 마일스톤을 지나며 새로 필요해지는 경우가 있다
바뀐 내용을 되짚어볼 수 없음
계획서가 최신화되면 이전에 뭐라고 적혀 있었는지 확인할 방법이 없어진다
02무엇을 만드는가
①
마일스톤별 최신화 점검·버전 스탬프
착수/Mcar/Proto/P1/P2/SoP 열마다 실제로 최신화됐을 때만 버전을 한 칸 올려 기록한다
②
v1 고정관념 탈피
v1은 착수 열이 아니라 그 행에서 처음 값이 채워지는 열이며, 끝까지 최신화가 없으면 v1이 계속 유지된다
③
변경 이력 전량 보존(R~V)
새 버전이 스탬프되는 순간, 직전까지의 내용이 히스토리 칸으로 그대로 이관되어 남는다
④
config 기반 신규 항목 자동 편입
새로 필요해진 항목은 config.py 구역 정의에 추가하면 엑셀·PPT 양쪽에 자동 반영된다
핵심 원리
버전 번호는 건너뛰기 금지(v1→v3 불가) + 이후 마일스톤 열에 더 낮은 버전이 있으면 순서 오류로 거부
내부 스냅샷
W열(숨김)이 "마지막 확정 시점"의 내용을 보관했다가, 다음 버전 스탬프 때 히스토리로 이관
03어떻게 동작하는가
1
내용 수정
H열(내용)을 수정하고 G열 상태를 진행/완료로 바꾼다
2
마일스톤 도래 시 최신화 여부 판단
해당 마일스톤에서 실제로 내용이 바뀌었는지 점검한다
3
버전 스탬프
바뀐 경우에만 착수~SoP 중 해당 마일스톤 열에 다음 버전을 입력한다
4
히스토리 이관
스탬프 순간, 스냅샷의 이전 내용이 히스토리 칸으로 옮겨지고 스냅샷은 현재 내용으로 갱신된다
5
검증 후 PPT 생성
버튼 클릭 시 1차 검증을 통과하면 Python pipeline이 최신 내용으로 PPT를 만든다
04기존 방식 vs 마일스톤 버전관리
구분
기존 방식 (v1 고정)
마일스톤 버전관리 (이번)
갱신 시점
프로젝트 초반 1회 작성 후 방치
마일스톤마다 최신화 필요 여부를 점검
버전 표시
버전 개념 없음 (v1 그대로)
실제 변경 시에만 버전을 1씩 증가
이전 내용
덮어써서 사라짐
히스토리 칸에 그대로 보존되어 대조 가능
심사 대응
"언제 확인했는지" 근거 없음
마일스톤별 점검·변경 이력 자체가 근거가 됨
버전이 v1에 계속 머물러 있어도, 그 자체가 "여러 마일스톤을 거치는 동안 실제로 바뀔 내용이 없었다"는 근거로 남는다.
05Before / After
이전 — 초반 작성 후 방치
사문서로 지적받음
프로젝트 초기에 쓴 계획서가 끝까지 v1으로 남아, 실제 진행과 괴리된 사문서로 지적받았다.
현재 — 마일스톤마다 점검+이력 보존
변경 여부와 이전 내용 모두 확인 가능
마일스톤마다 최신화 여부를 점검하고, 바뀐 내용과 이전 내용을 모두 확인할 수 있다.
06기대 효과
심사 대응력 향상
마일스톤별 점검·변경 이력 자체가 감사 대응 근거가 된다
신규 항목 누락 방지
나중에 필요해진 항목도 config 정의만 추가하면 놓치지 않고 반영된다
변경 추적 가능
이전 내용이 사라지지 않고 남아 무엇이 왜 바뀌었는지 확인할 수 있다
불필요한 버전 남발 방지
실제 변경이 없으면 버전을 올리지 않아, 버전 자체가 의미 있는 신호로 남는다
07유의할 점
  • 버전 값은 "v1, v2..." 형식만 허용되며, 번호를 건너뛰거나(v1→v3) 이후 마일스톤 열에 더 낮은 버전을 입력하면 자동으로 되돌려진다
  • 히스토리 이관은 새 버전이 스탬프되는 시점에만 일어나며, 내용을 여러 번 고치는 것 자체는 이관을 유발하지 않는다
  • 히스토리 저장 칸은 5개로 제한되어 있어, 다 차면 담당자에게 별도 문의가 필요하다
